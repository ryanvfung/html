## 2. Disagreements — and why

12. **B2's mechanism is wrong (finding right, physics wrong).** B says the collision means "every `border: var(--border-strong)` in components renders a color-as-width." There is no such width-position `border:` consumer. With the Tier 2 color winning (line 241 after line 200), the actual consumers — `outline: var(--border-strong) solid var(--focus-ring)` (lines 415, 491) and `border-width: var(--border-strong)` (line 540) — become *invalid at computed-value time*: `outline-style` falls back to `none` (no focus ring anywhere; Task 21's focus test at line 1205 fails) and `border-width` falls back to `medium`. Only color-position consumers survive (`kbd`, line 584; sidebar `border-inline-start`, line 636). B's alternative clause ("or the token display in `gen-spec.mjs` lies") is correct — the dedupe at line 906 keeps the first (width) occurrence — but B understates the primary harm: this is a shipped accessibility defect, not a display inconsistency.
13. **B4's ratio is off.** B computes ~2.7:1; #f8f7f7 (L ≈ 0.933) on #ff7700 (L ≈ 0.345) is ≈ **2.5:1**. Non-load-bearing (both fail the 3:1 large-text floor), but A's figure is the one to quote in a fix PR.
14. **Score: 6/10 (A) vs 7/10 (B).** B's deduction list (line 54) covers five defects plus two Review-Focus attribution mismatches. A's covers those plus the findings in section 3 below — F3, F5, F6, F7, F9, F10 each independently produce a failed gate or an unmet DoD. The one-point gap is exactly B's blind spots.
15. **B12 severity (MEDIUM vs A's "nit").** A concedes B's recovery note (`git checkout -- v6/dist`) is cheap and correct, and that B's staging hazard is real. A still rates it lower: the exposure window is a single task (Task 15), any later successful `npm run build` restores the tree, and no user-facing artifact is affected. Defensible either way; not a plan blocker.
16. **B8 is half-right and mis-framed.** B says Review Focus item 1 is "never tested." True — no `javaScriptEnabled: false` context exists in Task 21. But line 30 explicitly designates its own (weaker) pin: "Task 4 pins this by compiling `:root` defaults," and Task 4 does compile `:root, [data-theme="light"]` (line 236). The accurate finding is *the pin is static, never rendered* — no test loads a page with JS disabled and asserts a computed color — not that the promise went unacknowledged. B's proposed fix (zero-JS test + persistence round-trip + `prefers-color-scheme` branch) is right and A endorses it.
17. **B17 is unmoored.** "spec.pug ships without the skip link, header, and footer" is factually true (lines 946–978), but neither the plan nor anything either reviewer can cite requires the spec page to carry site chrome; A only observed spec's header-free state as a *masking factor* in F7 (it would pass the 320px test while the header fails). B offers no design/DoD citation. Keep it as a suggestion to the author, not a defect.

## 4. What B got wrong

33. **B13's premise is false.** "lint:html runs against `dist/*.html`, which doesn't exist on a fresh clone" ignores plan line 14: **`v6/dist/` is committed**. README is written in Task 23 (line 1302), long after Task 16 has produced `dist/*.html`, so a fresh clone of the shipped repo has those files and `npm run lint` works standalone. The gap exists only transiently mid-plan (before Task 16) — when no README exists yet to mislead anyone. A deliberately did not raise this finding.
34. **B16 misclassifies `--surface-overlay` as dead.** It is consumed: gen-spec's Review Focus #2 assertion (lines 907–908) uses it as the comma fixture, and Task 17 Step 2 verifies `overlay=rgba(22,20,19,0.55)` (line 922). The genuinely dead pair is `--elevation-strategy`/`--shadow-card` (A's F25) — one of which DESIGN.md line 1265 enshrines as a rule no code reads. B's fix ("defer them to v6.1") would delete a pinned assertion's subject.
35. **B3/B11's fixes are incomplete as written.** B's fix for the broken consumption model is "have README document both imports" — that pushes an `@import` of `_tokens.scss` (an `.scss`-named file) into the *consumer's* pipeline, contradicting README's "framework-free, no build step" framing (line 1307); the only self-contained fix is the import inside `_tailwind-theme.css` (or renaming it to `.css`, since the token file contains no SCSS syntax). And B11's fix ("count `var(--…)` in `dist/tailwind-probe.css`") presupposes the probe compiles and contains the lines — which is exactly what A's F3 shows it will not, under Task 20 Step 2 as written.
